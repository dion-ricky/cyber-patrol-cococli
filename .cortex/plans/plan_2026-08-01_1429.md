## Goal
Pull the ETL out of `web_scanner` into its own standalone containerized app, and run it as a scheduled **Snowpark Container Services (SPCS) job** — fully inside Snowflake, no external host/cron.

## Key findings from research
- SPCS job services (`EXECUTE JOB SERVICE`) run a container to completion, like a stored proc but with a full custom image — exactly what a batch ETL needs.
- Egress from a job requires the same **External Access Integration (EAI)** mechanism as UDFs/procs: `CREATE NETWORK RULE` (destination host:port, EGRESS) → `CREATE SECRET` (credentials) → `CREATE EXTERNAL ACCESS INTEGRATION` → pass `EXTERNAL_ACCESS_INTEGRATIONS = (...)` to `EXECUTE JOB SERVICE`.
- The container gets **Snowflake credentials automatically** (no secret needed for the Snowflake side): an OAuth token at `/snowflake/session/token` + `SNOWFLAKE_ACCOUNT`/`SNOWFLAKE_HOST` env vars, usable directly with `snowflake.connector.connect(authenticator='oauth', token=..., host=..., account=...)`.
- Images must live in a **Snowflake image repository** (`CREATE IMAGE REPOSITORY`) — SPCS can't pull from GHCR directly, so we push the built image there via `docker push`.
- `CREATE SERVICE`/`EXECUTE JOB SERVICE` cannot be run as `ACCOUNTADMIN` — needs a role with the right grants (compute pool, EAI, image repo, secret).
- Account already has a suspendable `SYSTEM_COMPUTE_POOL_CPU` (auto-resume, 300s auto-suspend) that a lightweight periodic job can reuse instead of a dedicated pool.
- The repo already has a convention for standalone apps living as siblings to `web_scanner` (see `data-ingest/`), each with its own `pyproject.toml`/Dockerfile — the new ETL app follows that pattern.
- `CYBERPATROL.RAW` schema/tables/stage/watermark table are already created in Snowflake (from the earlier step) and stay as the load target regardless of where the ETL runs.
